Experimental agent-scheduling engine

A constraint-aware scheduling reference for exploring how cost, latency, and load signals might improve task assignment against a simple round-robin baseline.

Evidence boundary: this is an experimental agent-scheduling engine evaluated with a synthetic benchmark. The results are not evidence from production agents, customer workloads, live model traffic, or an operated fleet.

The experimental question

Round-robin scheduling treats available workers uniformly even when their cost, response time, and current load differ. This experiment asks whether an explicit fitness score can use those signals to make a better assignment under a controlled workload.

The scheduling approach

Each candidate receives separate cost, latency, load, and affinity scores. A weighted objective selects the highest-scoring available candidate, while thresholds govern deferral and lifecycle decisions. Keeping the signals independent makes it possible to test constraint boundaries and vary weights without replacing the scheduler.

  • Cost fitness represents remaining budget headroom.
  • Latency fitness compares observed response time with the synthetic task target.
  • Load fitness penalizes candidates as simulated concurrency approaches a ceiling.
  • Affinity fitness represents a synthetic warm-context advantage for similar task shapes.

Synthetic benchmark results

In the recorded synthetic benchmark, the experimental scheduler reported 91.2% SLA compliance versus 78.3% for the round-robin baseline: a 16.5% relative improvement. It also reported 41% lower load variance across the simulated fleet.

Limitations beside the result: the task mix, worker profiles, latency behavior, budget ceiling, and load changes were simulated. A round-robin comparator is intentionally simple. The benchmark does not establish performance with real models, variable network conditions, queue backpressure, provider failures, customer traffic, or production economics.

Reference implementation

The Python reference implementation separates scoring dimensions from routing and lifecycle behavior. Its pytest suite exercises score calculation, spawn and retire decisions, and exact constraint boundaries such as a zero budget, a concurrency ceiling, and an expired synthetic SLA target.

What production validation would require

A production claim would require representative task traces, real model and provider behavior, controlled comparisons against stronger scheduling policies, cost and latency instrumentation, failure injection, queue-pressure tests, and observation over time. Until that evidence exists, the correct status is experiment.
